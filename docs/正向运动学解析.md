## 1. 正运动学是什么

给定关节配置 $q$（以及可选的速度 $v$、加速度 $a$），求每个关节坐标系相对世界系的**位姿** ${}^0M_i$，以及它的**空间速度** $v_i$、**空间加速度** $a_i$。

这是所有算法的地基：雅可比、RNEA、CRBA、碰撞检测、IK 里的 $M_6(q)$，都靠它先把 `data.oMi[]`（以及 `data.v[]`、`data.a[]`）填好。

Pinocchio 提供三个重载，按"算到几阶"区分：

| 调用 | 填充的 `data` 字段 | 数学量 |
|---|---|---|
| `forwardKinematics(model, data, q)` | `oMi`, `liMi` | 位姿 ${}^0M_i$ |
| `forwardKinematics(model, data, q, v)` | `+ v` | 空间速度 $v_i$ |
| `forwardKinematics(model, data, q, v, a)` | `+ a` | 空间加速度 $a_i$ |

三者共享同一套**从根到叶的递推**，只是每往下一阶多算一层导数。

> ⚠️ `forwardKinematics` **只更新关节坐标系**（`oMi`），不更新 frame（`oMf`）、不算雅可比、不算能量。frame 需要额外调 `updateFramePlacements`，雅可比要 `computeJointJacobians`。

## 2. 递推的三块积木：liMi / oMi / jointPlacements

Pinocchio 的运动树里，每个关节 $i$ 有一个父关节 $\lambda(i)=$ `model.parents[i]`，且**满足 `parents[i] < i`**（DFS 编号，见 [multibody 解析 §2.4](multibody子系统解析.md)）。这个不变量保证：正序 `for i=1..njoints` 遍历时，父关节 $\lambda(i)$ 必然已经算完 —— 这正是递推能一趟扫完的关键。

三个 SE(3) 量：

- **`model.jointPlacements[i]`**：父关节体坐标系 → 关节 $i$ 的**固定安装位姿** ${}^{\lambda}M_i^{\text{fix}}$。纯几何常量（URDF 里 `<origin>`），不随 $q$ 变。
- **`jdata.M()`**：关节自身的运动，即关节坐标系相对其"零位安装点"的位姿 ${}^{\text{fix}}M_i(q_i)$。由 `jmodel.calc(jdata, q)` 算出，**只依赖本关节的那几维 $q_i$**。比如转动关节就是绕轴转 $q_i$ 的旋转。
- **`data.liMi[i]`**：父关节 → 关节 $i$ 的**完整相对位姿**：

$$
\texttt{liMi[i]} = {}^{\lambda}M_i = \underbrace{{}^{\lambda}M_i^{\text{fix}}}_{\texttt{jointPlacements[i]}}\cdot\underbrace{{}^{\text{fix}}M_i(q_i)}_{\texttt{jdata.M()}}
$$

对应代码：

```cpp
jmodel.calc(jdata.derived(), q.derived());          // 算出 jdata.M()
data.liMi[i] = model.jointPlacements[i] * jdata.M();  // 组合成父→子相对位姿
```

- **`data.oMi[i]`**：世界系 → 关节 $i$ 的**绝对位姿** ${}^0M_i$，由链式复合得到：

$$
{}^0M_i = {}^0M_{\lambda(i)}\cdot{}^{\lambda}M_i
\qquad(\texttt{oMi[i] = oMi[parent] * liMi[i]})
$$

```cpp
if (parent > 0)
  data.oMi[i] = data.oMi[parent] * data.liMi[i];
else
  data.oMi[i] = data.liMi[i];      // parent==0 即 universe，oMi[0]=Id，省一次乘法
```

`parent > 0` 的分支只是把"父是世界根（universe，id=0）"这种情形抠出来省一次矩阵乘：此时 ${}^0M_i = {}^{\lambda}M_i$。

**一句话**：`jointPlacements` 是骨架常量，`jdata.M()` 是关节变量，二者乘出局部相对位姿 `liMi`，再沿树复合成全局位姿 `oMi`。

## 3. 零阶：只算位姿 `ForwardKinematicZeroStep`

最简单的重载，核心 `algo` 就是 §2 那几行：

```cpp
const JointIndex & i = jmodel.id();
const JointIndex & parent = model.parents[i];

jmodel.calc(jdata.derived(), q.derived());            // ① 解本关节：得 jdata.M()

data.liMi[i] = model.jointPlacements[i] * jdata.M();  // ② 局部相对位姿

if (parent > 0)                                       // ③ 复合成全局位姿
  data.oMi[i] = data.oMi[parent] * data.liMi[i];
else
  data.oMi[i] = data.liMi[i];
```

驱动循环（在 `impl::forwardKinematics` 里）：

```cpp
for (JointIndex i = 1; i < model.njoints; ++i)      // 从 1 开始：0 是 universe
  Algo::run(model.joints[i], data.joints[i], ArgsType(model, data, q));
```

- 循环**从 1 开始**：关节 0 是世界根 universe，`oMi[0]=Identity` 恒定，无需计算。
- 因为 `parents[i] < i`，正序遍历天然满足"先父后子"，一趟 $O(n)$ 扫完，无需显式递归或拓扑排序。

**入口的尺寸检查**：

```cpp
PINOCCHIO_CHECK_ARGUMENT_SIZE(q.size(), model.nq, "...");
```

注意是 `model.nq`（配置维度，流形维度），不是 `model.nv`。因为 $q$ 活在流形上（四元数、$(\cos,\sin)$ 等），$n_q\ge n_v$，详见 [multibody 解析 §2.2](multibody子系统解析.md)。

## 4. 访问者模式：`JointUnaryVisitor` 如何分派关节类型

上面 `algo` 的第一行 `jmodel.calc(...)` 是多态的：转动关节、平动关节、球关节、浮动基……各自的 `calc` 数学完全不同。Pinocchio 用 **boost::fusion 静态访问者**在编译期分派，零虚函数开销。

```cpp
struct ForwardKinematicZeroStep
: fusion::JointUnaryVisitorBase<ForwardKinematicZeroStep<...>>   // CRTP
{
  typedef boost::fusion::vector<const Model&, Data&, const ConfigVectorType&> ArgsType;

  template<typename JointModel>          // ← 每种关节类型实例化一份
  static void algo(const JointModelBase<JointModel> & jmodel,
                   JointDataBase<...> & jdata, ...) { /* 上面那段 */ }
};
```

- `model.joints[i]` 是一个 **variant**（能装下所有关节类型的联合体）。`Algo::run(...)` 内部对它做 `boost::apply_visitor`，在运行期确定实际类型后，**跳到编译期为该类型生成的 `algo`**。
- `ArgsType` 把 `(model, data, q)` 打包传给访问者 —— 因为 `apply_visitor` 只接受"一个 variant + 一个可调用对象"，额外参数得先塞进 fusion vector 里。
- 好处：`jmodel.calc` 会被内联成该关节的具体公式（转动关节直接写 `sin/cos`），没有虚表跳转。这是 Pinocchio "模板化零开销" 设计的核心，详见 [multibody 解析 §4](multibody子系统解析.md)。

三个重载 `ZeroStep / FirstStep / SecondStep` 结构完全一样，只是 `ArgsType` 依次多带 `v`、`a`，`algo` 里多算速度/加速度层。

## 5. 一阶：位姿 + 空间速度

`ForwardKinematicFirstStep::algo` 在零阶基础上多两行：

```cpp
jmodel.calc(jdata.derived(), q.derived(), v.derived());   // 注意：带 v 的 calc

data.v[i] = jdata.v();                                    // ① 关节自身贡献
data.liMi[i] = model.jointPlacements[i] * jdata.M();

if (parent > 0) {
  data.oMi[i] = data.oMi[parent] * data.liMi[i];
  data.v[i] += data.liMi[i].actInv(data.v[parent]);       // ② 加上父关节速度（搬到本系）
} else
  data.oMi[i] = data.liMi[i];
```

调用前先 `data.v[0].setZero()`（世界根不动）。

### 5.1 速度递推公式

空间速度在**关节 $i$ 自己的体坐标系**下满足：

$$
\boxed{\,v_i = {}^iX_{\lambda}\, v_{\lambda} + v_{J,i}\,}
$$

- $v_{J,i}=$ `jdata.v()` $= S_i(q)\,\dot q_i$：**本关节引入的相对运动**（运动子空间 $S_i$ 乘关节速度）。转动关节就是 $\dot q_i$ 沿转轴的角速度。
- ${}^iX_{\lambda}\,v_{\lambda}=$ `liMi[i].actInv(data.v[parent])`：把父关节的速度**从父体系搬运到本体系**。

### 5.2 为什么是 `actInv` 而不是 `act`

关键在**坐标系方向**。`data.liMi[i]` $={}^{\lambda}M_i$ 是"父→子"的位姿，它的伴随 `act` 把向量从**子系搬到父系**。而我们要的是反过来：把父系的 $v_\lambda$ 表达到子系，所以用逆伴随 `actInv`：

$$
{}^iX_{\lambda} = ({}^{\lambda}X_i)^{-1} = \big(\mathrm{Ad}_{{}^{\lambda}M_i}\big)^{-1}
\;\Longrightarrow\; \texttt{liMi[i].actInv}(\cdot)
$$

直觉：速度是"随体量"。父连杆带着子连杆一起动，这份"被带动"的速度本来记在父系里，要并进子系的账本就得先做一次系变换 ${}^iX_\lambda$。加上子关节自转 $v_{J,i}$，就是子系里看到的总速度。

> 这套 `actInv(父) + 本关节` 的模式，在 RNEA/ABA 里反复出现，是刚体树递推的通用骨架。

## 6. 二阶：位姿 + 速度 + 空间加速度

`ForwardKinematicSecondStep::algo` 在一阶基础上再加加速度层：

```cpp
data.a[i] = jdata.S() * jmodel.JointMappedVelocitySelector(a)   // ①本关节加速度贡献
          + jdata.c()                                           // ②关节偏置加速度
          + (data.v[i] ^ jdata.v());                            // ③速度耦合（李括号）
data.a[i] += data.liMi[i].actInv(data.a[parent]);               // ④父加速度搬到本系
```

调用前 `data.v[0].setZero(); data.a[0].setZero();`

### 6.1 加速度递推公式

对速度递推 $v_i = {}^iX_\lambda v_\lambda + S_i\dot q_i$ 求时间导数（注意 ${}^iX_\lambda$ 随时间变、$S_i$ 也可能随 $q$ 变）：

$$
\boxed{\,a_i = {}^iX_{\lambda}\,a_{\lambda} + S_i\,\ddot q_i + \dot S_i\,\dot q_i + v_i\times v_{J,i}\,}
$$

逐项对上代码：

| 公式项 | 代码 | 含义 |
|---|---|---|
| $S_i\,\ddot q_i$ | `jdata.S() * JointMappedVelocitySelector(a)` | 本关节加速度经运动子空间映射到空间加速度 |
| $\dot S_i\,\dot q_i$ | `jdata.c()` | **关节偏置加速度**（运动子空间随构型变化引起，转动/平动关节为 0，欧拉角关节非 0；深入见 §6.3）|
| $v_i\times v_{J,i}$ | `data.v[i] ^ jdata.v()` | 空间速度叉乘（$se(3)$ 李括号 $\mathrm{ad}_{v_i}v_{J,i}$），本系速度与关节速度的耦合 |
| ${}^iX_\lambda a_\lambda$ | `liMi[i].actInv(data.a[parent])` | 父加速度搬到本系（同 §5.2 用 `actInv`）|

- `JointMappedVelocitySelector(a)`：从**整机**加速度向量 $a\in\mathbb R^{n_v}$ 里，切出属于本关节的那几维 $\ddot q_i$。之所以叫 "MappedVelocity"，是为了兼容 mimic 关节（被驱动维会映射到主动维），普通关节就是普通的 `a.segment(idx_v, nv)`。
- ⚠️ 这里的 `data.a[i]` 是**空间加速度**（spatial / 6D，含"李群修正"的那一版），**不是**日常直觉里的"质点线加速度"。二者差一个 $v\times v$ 项，见 §10。

### 6.2 为什么空间加速度里没有离心项，却仍要 $v\times v_J$

空间加速度的定义 $a=\dot v$（体系下对 6D twist 直接求导）本身**不含**离心/向心项 —— 这正是它数学上优美（对速度线性、可叠加）的原因。式中的 $v_i\times v_{J,i}$ 不是离心力，而是"求导时坐标系在转"带出来的**运动学耦合项**。真正的离心加速度要到 §10 的经典加速度里才出现。

### 6.3 `jdata.c()` 深入：$c=\dot S\dot q$ 与"为什么大多数关节它是 0"

`jdata.c()`（类型 `Bias_t`）就是 §6.1 里的第 ③ 项 $\dot S_i\dot q_i$，称为**关节偏置加速度**（bias acceleration）。

**定义来历**：关节引入的相对速度是 $v_{J,i}=S_i(q)\dot q_i$（见 §5.1）。对它求时间导数：

$$
\dot v_{J,i}=\frac{d}{dt}\big(S_i\dot q_i\big)
=\underbrace{S_i\ddot q_i}_{\text{随}\,\ddot q}+\underbrace{\dot S_i\dot q_i}_{=\,c_i\ (\texttt{jdata.c})}
$$

$c_i$ 是"即使 $\ddot q_i=0$（匀速转动），关节处仍存在的那份加速度"，**只跟 $\dot q$ 的二次项有关**，与 $\ddot q$ 无关。它是否为零，完全取决于**运动子空间 $S_i$ 是否随构型 $q$ 变化**。

#### 6.3.1 关键判据：$S$ 是否恒定，取决于"速度 $\dot q$"是哪种坐标

$S$ 的作用是把关节的**速度坐标 $\dot q$** 映射到**体系下的空间速度 twist**：$v_J=S(q)\dot q$。于是：

- $\dot q$ **本身就是体系 twist**（李代数元素）→ $S$ 是恒等/常数投影 → $\dot S=0$ → $c=0$；
- $\dot q$ 是**某张坐标图（chart）上参数的时间导数**（如欧拉角变化率）→ $S$ 是这张图的几何雅可比，**随构型旋转** → $\dot S\ne0$ → $c\ne0$。

源码里用 `Bias_t` 的类型直接编码了这个区别（`MotionZeroTpl` 是空类型，参与运算被编译器优化成 0，零存储零指令）：

| 关节 | 旋转/运动群 | 速度 $\dot q$ 的语义 | `Bias_t` | $S$ | $c$ |
|---|---|---|---|---|---|
| revolute / prismatic | — | 绕**固定体轴**的角/线速度 | `MotionZero` | 常数 | $\equiv0$ |
| free-flyer (SE3) | SE(3) | **体系 6D twist 本身** | `MotionZero` | $I_6$ | $\equiv0$ |
| spherical（四元数） | SO(3) | **体系角速度 $\omega$ 本身** | `MotionZero` | $[0;I_3]$ | $\equiv0$ |
| **spherical-ZYX（欧拉角）** | SO(3) | **欧拉角变化率 $\dot q$** | `MotionSpherical` | $E(q)$ | $\ne0$ |

> **注意后两行：同一个 SO(3)，一个 $c=0$ 一个 $c\ne0$。** 差异不在"关节转什么"，而在于速度变量**是不是天生活在体系里**。这正是 Pinocchio 让 $n_q\ne n_v$、把速度放进**李代数**的深层动机之一——换来正确的关节（SE3/SO3）拥有**常数 $S$**，从而 $c=0$、无奇异。见 [multibody 解析 §2.2](multibody子系统解析.md)。

- **free-flyer**：$n_q=7$（位置+四元数）但 $n_v=6$，这 6 维速度**直接定义为体系 twist**，不是 $\dot q$（位置/四元数的时间导数）。映射恒等，$S\equiv I_6$，$\dot S=0$。四元数的时间演化由 `integrate`（$q\oplus v$）负责，**不经过 $S$**。
- **四元数球关节**：$v=$ 体系角速度 $\omega$，$S=[0;I_3]$ 常数，$c=0$。

#### 6.3.2 $\dot S\ne0$ 的实例：spherical-ZYX（欧拉角）

ZYX 欧拉角球关节 $n_q=n_v=3$，$q=(q_0,q_1,q_2)$ 是三个欧拉角，$\dot q$ 是**欧拉角变化率**（不是体系角速度）。二者关系是随角度变的矩阵 $E(q)$：$\omega_{\text{body}}=E(q)\dot q$，即 $S=E(q)$。

其旋转矩阵（[joint-spherical-ZYX.hxx:432](../include/pinocchio/src/multibody/joint/joint-spherical-ZYX.hxx#L432)，逐元素验证）为：

$$
R(q)=R_z(q_0)\,R_y(q_1)\,R_x(q_2)
$$

即**内旋 $Z\to Y'\to X''$**（等价于外旋 $X\to Y\to Z$），也就是经典 **yaw($q_0$)–pitch($q_1$)–roll($q_2$)**。运动子空间（[joint-spherical-ZYX.hxx:435](../include/pinocchio/src/multibody/joint/joint-spherical-ZYX.hxx#L435)）按列（对 $\dot q_0/\dot q_1/\dot q_2$）拆开：

$$
S=\begin{bmatrix} -s_1 & 0 & \mathbf{1}\\ c_1 s_2 & c_2 & \mathbf{0}\\ c_1 c_2 & -s_2 & \mathbf{0}\end{bmatrix}
$$

- **$\dot q_2$ 列（X，最内层）$=(1,0,0)^\top$：常数**。这个轴就是当前体系 X 轴，零变换。
- **$\dot q_1$ 列 $=(0,c_2,-s_2)^\top$：依赖 $q_2$**。Y 轴要被内层 X($q_2$)旋转才落到体系。
- **$\dot q_0$ 列 $=(-s_1,c_1s_2,c_1c_2)^\top$：依赖 $q_1,q_2$**。Z 轴要连过 Y、X 两层。

**越外层的欧拉轴、$S$ 列越依赖内层角度 → $\dot S\ne0$**。

#### 6.3.3 为什么"依赖计数"从内层 $q_2$ 起，而非从 $q_0$ 起

关键：Pinocchio 的 $S$ 表达在**体系（LOCAL）**，而体系是 ZYX 链的**内层末端**。把每个率的轴搬进体系，要左乘 $R^\top=R_x(q_2)^\top R_y(q_1)^\top R_z(q_0)^\top$。先在世界系写角速度，再转体系：

$$
\omega_{\text{world}}=\dot q_0\,\hat z+\dot q_1\,R_z\hat y+\dot q_2\,R_zR_y\hat x,\qquad
\omega_{\text{body}}=R^\top\omega_{\text{world}}=S\dot q
$$

逐项约分（用 $R_x^\top\hat x=\hat x$ 等"旋转不动自己轴"）：

$$
\begin{aligned}
\dot q_2:&\ R^\top R_zR_y\hat x=R_x(q_2)^\top\hat x=\hat x=(1,0,0)^\top &&\textbf{常数（隔 0 层）}\\
\dot q_1:&\ R^\top R_z\hat y=R_x(q_2)^\top\hat y=(0,c_2,-s_2)^\top &&\textbf{依赖}\,q_2\,\textbf{（隔 1 层）}\\
\dot q_0:&\ R^\top\hat z=R_x(q_2)^\top R_y(q_1)^\top\hat z=(-s_1,c_1s_2,c_1c_2)^\top &&\textbf{依赖}\,q_1,q_2\,\textbf{（隔 2 层）}
\end{aligned}
$$

决定"依赖几个角"的，是**这个轴到体系之间还隔着几层旋转**：$q_2$ 隔 0 层（就是体系）、$q_1$ 隔 1 层、$q_0$ 隔 2 层。体系是内层末端，故计数自内向外。

> **反过来**：若 $S$ 表达在**世界系**（不左乘 $R^\top$），则 $\dot q_0$ 列 $=\hat z=(0,0,1)$ 变常数、$\dot q_2$ 列依赖 $q_0,q_1$——完全对称翻转。**哪端是常数列，取决于 $S$ 表达在哪个系：与谁相邻的欧拉轴就是常数。**

#### 6.3.4 附带代价：万向节死锁

$q_1=\pm\pi/2$（俯仰 90°）时 $c_1=0$，$S$ 的 $\dot q_0$ 列与 $\dot q_2$ 列共线，$S$ 掉秩——**万向节死锁（gimbal lock）**，欧拉角参数化的固有病。四元数版本（$S$ 常数）没有此问题，这也是 Pinocchio 默认球关节用四元数的原因。

## 7. `updateGlobalPlacements`：只刷新 oMi

```cpp
void updateGlobalPlacements(model, data) {
  for (JointIndex i = 1; i < model.njoints; ++i) {
    const JointIndex & parent = model.parents[i];
    if (parent > 0) data.oMi[i] = data.oMi[parent] * data.liMi[i];
    else            data.oMi[i] = data.liMi[i];
  }
}
```

它**只做 §2 的第③步**（`oMi = oMi[parent] * liMi`），假设 `liMi` 已经是最新的，不重算 `jmodel.calc`。

**用途**：RNEA / ABA 这类动力学算法内部只维护 `liMi`（局部量足够递推），跑完后 `oMi` 可能是脏的。若接着要用全局位姿（画图、算 frame、碰撞），调一次 `updateGlobalPlacements` 就地补全，比重跑 `forwardKinematics` 便宜（省掉每关节的 `calc`）。

## 8. `getRelativePlacement`：两关节相对位姿（LOCAL O(n) vs WORLD O(1)）

求 ${}^{\text{ref}}M_{\text{target}}$（target 关节在 ref 关节系下的位姿）。两种约定：

### 8.1 WORLD 约定 —— O(1)

```cpp
case Convention::WORLD:
  return data.oMi[jointIdRef].actInv(data.oMi[jointIdTarget]);
```

直接用全局位姿：${}^{\text{ref}}M_{\text{target}} = ({}^0M_{\text{ref}})^{-1}\,{}^0M_{\text{target}}$。一次求逆一次乘，$O(1)$。**前提是 `oMi` 已被 `forwardKinematics` 更新**。

### 8.2 LOCAL 约定 —— O(n)

不碰全局 `oMi`，只用局部 `liMi` 沿树往上爬到**最近公共祖先**（LCA），两边分别累积再拼接：

```cpp
size_t ancestor_ref, ancestor_target;
findCommonAncestor(model, jointIdRef, jointIdTarget, ancestor_ref, ancestor_target);

// 从 ref 沿支撑链（supports[ref]）回溯到公共祖先，累积 ancestorMref
for (size_t i = supports[jointIdRef].size()-1; i > ancestor_ref; i--) {
  const JointIndex j = supports[jointIdRef][i];
  ancestorMref = data.liMi[j].act(ancestorMref);
}
// 同理累积 ancestorMtarget
...
return ancestorMref.actInv(ancestorMtarget);   // = (aMref)^{-1} * aMtarget
```

- `model.supports[j]` 是从根到 $j$ 的关节路径（见 [multibody 解析 §2.4](multibody子系统解析.md)）。`findCommonAncestor` 找到两条路径的分叉点 LCA=$a$，并返回它在各自 `supports` 里的下标。
- 循环把 ref 一侧从叶到 $a$ 的所有 `liMi` **左乘累积**，得到 ${}^aM_{\text{ref}}$；target 一侧同理得 ${}^aM_{\text{target}}$。
- 最后 ${}^{\text{ref}}M_{\text{target}} = ({}^aM_{\text{ref}})^{-1}\,{}^aM_{\text{target}}$，公共祖先 $a$ 之上的部分**自动约掉**，无需求全局位姿。

**为什么留 LOCAL 这条 O(n) 路？** 文档里点明：当 `aba`/`crba` 也以 LOCAL 约定运行时，`oMi` 可能没被维护（只有 `liMi` 是可信的），此时只能走 LOCAL。若 `oMi` 是新的，WORLD 更快。

## 9. `getVelocity` / `getAcceleration`：参考系变换

`data.v[i]`、`data.a[i]` 存的是 **LOCAL**（关节自身体坐标系）下的量。这两个 getter 把它转到用户想要的参考系：

```cpp
MotionTpl getVelocity(model, data, jointId, rf) {
  switch (rf) {
  case LOCAL:               return data.v[jointId];
  case WORLD:               return data.oMi[jointId].act(data.v[jointId]);
  case LOCAL_WORLD_ALIGNED: return Motion(oMi.rotation()*v.linear(),
                                          oMi.rotation()*v.angular());
  }
}
```

三种参考系（`ReferenceFrame`）的区别，是"**原点在哪 + 坐标轴朝哪**"：

| 参考系 | 原点 | 坐标轴朝向 | 变换 |
|---|---|---|---|
| **LOCAL** | 关节 $i$ 处 | 关节 $i$ 的体轴 | 恒等（直接返回 `data.v[i]`）|
| **WORLD** | 世界原点 O | 世界轴 | `oMi.act(v)`：完整伴随 $\mathrm{Ad}_{{}^0M_i}$ |
| **LOCAL_WORLD_ALIGNED** | 关节 $i$ 处 | 世界轴 | 只转朝向：线/角部分各乘 `oMi.rotation()` |

- **WORLD**：`act` 用完整 SE(3) 伴随，既转朝向 $R$ 又因原点平移把角速度耦合进线速度（$v_{\text{lin}}\!\to\! R v_{\text{lin}} + p\times R v_{\text{ang}}$）。这是"整个量搬到世界原点表达"。
- **LOCAL_WORLD_ALIGNED**（常记作 `aligned` 或 `a`）：原点仍在关节处，**只把三个轴旋到跟世界平行**。所以线、角部分各自左乘 $R$，没有平移耦合。机器人学里"末端在世界系下的速度/力"通常指这个 —— 位置还是末端点，但方向读数是世界方向。这也是雅可比 `LOCAL_WORLD_ALIGNED` 的默认语义。

`getAcceleration` 逻辑与之逐字相同，只是把 `data.v` 换成 `data.a`。

## 10. `getClassicalAcceleration`：经典加速度 vs 空间加速度

```cpp
MotionTpl getClassicalAcceleration(model, data, jointId, rf) {
  Motion vel = getVelocity(model, data, jointId, rf);
  Motion acc = getAcceleration(model, data, jointId, rf);
  acc.linear() += vel.angular().cross(vel.linear());   // ← 关键修正项
  return acc;
}
```

### 10.1 两种加速度差在哪

- **空间加速度**（spatial，`data.a`）：twist 的直接时间导数 $a=\dot v$。数学上对速度**线性**、可叠加，是递推/动力学推导的自然对象，但**不等于**质点的物理线加速度。
- **经典加速度**（classical）：坐标系原点那个物质点的**真实线加速度** $\dot v_{\text{lin}}^{\text{物理}}$（你拿加速度计贴在那点测到的值）。

二者的线加速度部分相差一个 $\omega\times v_{\text{lin}}$：

$$
\boxed{\,a_{\text{classical}}^{\text{lin}} = a_{\text{spatial}}^{\text{lin}} + \omega\times v_{\text{lin}}\,}
$$

其中 $\omega=$ `vel.angular()`（角速度），$v_{\text{lin}}=$ `vel.linear()`。角加速度部分两者相同（不修正）。

### 10.2 为什么差这一项

空间速度的线部分 $v_{\text{lin}}$ 是"体系原点相对世界、但**在动系里表达**"的速度。对它求导时，动系本身在以 $\omega$ 旋转，按转动坐标系求导法则（$\frac{d}{dt}\big|_{\text{world}} = \frac{d}{dt}\big|_{\text{body}} + \omega\times$），就会多出 $\omega\times v_{\text{lin}}$ —— 这正是**向心/离心加速度**项。空间加速度把它"藏"起来了（换来对速度线性的好处），经典加速度把它加回来，得到物理真实值。

> 记忆点：**空间加速度**利于算法推导（线性、可叠加）；**经典加速度**才是加速度计读数（含离心项）。做碰撞/接触、需要真实惯性力时用经典。

## 11. 复杂度与调用约定

- **`forwardKinematics`**：$O(n)$，一趟根→叶递推（$n=$ 关节数）。零/一/二阶分别多算速度、加速度层，常数略增。
- **`getRelativePlacement`**：WORLD $O(1)$，LOCAL $O(n)$（爬树到 LCA）。
- **`getVelocity/Acceleration/ClassicalAcceleration`**：$O(1)$，只做一次参考系变换。

**调用顺序铁律**（源码 `@warning` 反复强调）：

1. 用 `getVelocity` 前，必须先跑过**一阶或二阶** `forwardKinematics(q, v[, a])`（否则 `data.v` 是脏的）。
2. 用 `getAcceleration` / `getClassicalAcceleration` 前，必须先跑过**二阶** `forwardKinematics(q, v, a)`。
3. `getRelativePlacement(WORLD)` 前，`oMi` 必须是新的（跑过 `forwardKinematics` 或 `updateGlobalPlacements`）。

尺寸检查：$q$ 查 `model.nq`，$v$/$a$ 查 `model.nv`（$n_q\ge n_v$，流形维 vs 切空间维）。

## 12. 一句话总结

正运动学 = **一趟 $O(n)$ 根→叶递推**，核心三行：

$$
\texttt{liMi}={}^\lambda M_i^{\text{fix}}\cdot M(q_i),\quad
\texttt{oMi}=\texttt{oMi[parent]}\cdot\texttt{liMi},\quad
v_i=\texttt{liMi.actInv}(v_\lambda)+S_i\dot q_i
$$

- **位姿**沿树复合 SE(3)；**速度**用 `actInv` 把父量搬进本系再叠本关节；**加速度**再加 $S\ddot q + \dot S\dot q + v\times v_J$。
- 关节类型的差异由 `jmodel.calc` 通过**编译期访问者**零开销分派。
- `data.v/a` 存 LOCAL，getter 转到 WORLD / LOCAL_WORLD_ALIGNED；**经典加速度**比空间加速度多一个离心项 $\omega\times v_{\text{lin}}$。
