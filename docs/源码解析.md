## 1. 显式模板实例化 `.cpp`：到底在干什么（以 kinematics.cpp 为例）

**涉及文件**：[../src/algorithm/kinematics.cpp](../src/algorithm/kinematics.cpp)
**关联指南**：[§11.1 三层文件布局](../PINOCCHIO_GUIDE.md)、[§11.2 Tpl+context](../PINOCCHIO_GUIDE.md)、[§11.4 JointCollectionTpl](../PINOCCHIO_GUIDE.md)

### 1.1 这段代码在整个机制里的位置

三层文件布局：`.hpp`（声明）→ `.hxx`（模板实现）→ **`.cpp`（对默认标量做显式实例化）**。
本文件属于**第三层**。它**不写任何算法逻辑**，只是命令编译器："把这些模板函数针对 `double` 版本
**提前编译一份**，塞进 `libpinocchio.so` 并导出符号。"

文件顶部的两行 include 是前提：

```cpp
#include "pinocchio/src/context/template-instantiation.hxx"
#include "pinocchio/algorithm/kinematics.hpp"   // 它末尾又 #include 了 kinematics.hxx
```

> **关键**：include 了 `kinematics.hpp`，而 `.hpp` 末尾又 `#include ".../kinematics.hxx"`，
> 所以模板的**完整定义在本 `.cpp` 里可见**——只有定义可见，才能做实例化。

### 1.2 逐行拆解一条

以 `forwardKinematics` 的第一条（只传 `q` 的重载）为例：

```cpp
template PINOCCHIO_EXPLICIT_INSTANTIATION_DEFINITION_DLLAPI void forwardKinematics<
  context::Scalar,              // = double
  context::Options,             // = 0
  JointCollectionDefaultTpl,    // = 默认关节目录
  Eigen::Ref<const context::VectorXs>>(   // q 的类型：对 double 动态向量的只读引用
  const Model &, Data &, const Eigen::MatrixBase<Eigen::Ref<const context::VectorXs>> &);
```

| 片段 | 含义 |
|------|------|
| `template ... void forwardKinematics<...>(...);` | 开头 `template` 关键字 + 结尾**没有函数体**（直接分号）→ C++ 的**显式实例化定义**语法（既非声明、也非调用） |
| `context::Scalar` / `context::Options` | 即 `double` / `0`，来自 context 开关（见 §11.2） |
| `JointCollectionDefaultTpl` | 默认关节类型目录（见 §11.4） |
| `Eigen::Ref<const context::VectorXs>` | 模板第 4 个参数 `ConfigVectorType`（`q` 的具体类型）。用 `Eigen::Ref<const...>` 而非 `VectorXd`，是为了让 numpy 切片、Eigen 块表达式等也能**零拷贝**匹配 |
| `PINOCCHIO_EXPLICIT_INSTANTIATION_DEFINITION_DLLAPI` | 宏，展开成平台相关的**符号导出属性**（Windows `__declspec(dllexport)`、Linux visibility），让实例化出的符号**能被 `.so`/`.dll` 导出、供外部链接** |

### 1.3 为什么同一个 `forwardKinematics` 出现三次

前三条是**同名、不同参数个数**的三个重载：

```cpp
forwardKinematics<..., q类型>               // 只传 q      → 只更新 data.oMi
forwardKinematics<..., q类型, v类型>        // 传 q, v     → 同时算速度 data.v
forwardKinematics<..., q类型, v类型, a类型>  // 传 q, v, a  → 同时算加速度 data.a
```

对应指南 §4.1 的三个重载。**每种参数组合都是一个独立模板实例**，编译器不会自动帮你把用不到的组合
编进库，所以必须**逐个**显式实例化。它们都在 `namespace impl {}` 里——真正的实现（访问者）放在
`impl`，对外干净接口在外层（见 §11.3）。

### 1.4 后半段的 getVelocity / getAcceleration 等

```cpp
template ... SE3Tpl<...>    getRelativePlacement<context::Scalar, ...>(const Model&, const Data&, ...);
template ... MotionTpl<...> getVelocity<context::Scalar, ...>(...);
template ... MotionTpl<...> getAcceleration<...>(...);
template ... MotionTpl<...> getClassicalAcceleration<...>(...);
```

同理，只是这些函数**不接收 `q`**（只从已算好的 `data` 里取结果），因此没有 `ConfigVectorType` 那个额外
模板参数，模板参数列表只有 `<Scalar, Options, JointCollection>` 三个；返回类型 `SE3Tpl`/`MotionTpl`
也一并指定为 double 版。

### 1.5 为什么要费这个劲——一句话总结

**为了编译速度 + 动态库导出**。模板实现全在头文件里，若不预实例化，则**每个** include
`kinematics.hpp` 的用户 `.cpp` 都要从头把 double 版 FK 编一遍。Pinocchio 在此 `.cpp` 里**一次性编好
double 版**、导出符号进 `libpinocchio.so`，下游项目直接链接现成符号即可。

这也串起了 §11.2 的那条线：

```
切换 context → context::Scalar 变 → 这里实例化的就变成新标量版 → 产出的库也换标量
```

例如构建 `libpinocchio_casadi` 时 `context::Scalar` 变成 `casadi::SX`，**这段代码一字不改**，
实例化出来的就是 CasADi 符号版的 `forwardKinematics`。

### 1.6 读源码启示

看到 `.cpp` 里成片的 `template ... <context::Scalar, ...>(...);` 时可**直接跳过**——它不是逻辑代码，
而是一张"预编译清单"。真正的算法实现永远在同名 `.hxx`（此处即
[../include/pinocchio/src/algorithm/kinematics.hxx](../include/pinocchio/src/algorithm/kinematics.hxx)）。

## 2. `ModelTpl::cast()` 的模板写法（四个 C++ 惯用法）

**涉及文件**：[../include/pinocchio/src/multibody/model.hxx](../include/pinocchio/src/multibody/model.hxx)（`ModelTpl::cast()`，约 1120-1195 行）
**关联指南**：[§11.2 Tpl+context / cast / autodiff](../PINOCCHIO_GUIDE.md)

`cast()` 把 `ModelTpl<Scalar,...>` 变成 `ModelTpl<NewScalar,...>`。它的**功能**（逐字段重造模型）
在指南 §11.2「玩具 2」已讲；这里专门解析它**叠加的 4 个 C++ 模板写法**，读懂后满库同类代码都不再陌生。

### 2.1 两行 `template<...>` 头 —— 类模板的成员模板，类外定义

```cpp
template<typename Scalar, int Options, template<typename, int> class JointCollectionTpl> // ← 外层：类的模板参数
template<typename NewScalar>                                                             // ← 内层：成员函数自己的模板参数
typename CastType<...>::type
ModelTpl<Scalar, Options, JointCollectionTpl>::cast() const
```

`cast` 是"模板类里的模板成员函数"。写在类**外面**时，C++ 要求把两层模板参数**分成两行 `template<>` 头**：
上面一行对应类 `ModelTpl`，下面一行对应成员 `cast` 自己的 `NewScalar`。**不能合并成一行**。
（写在类内部则只需一行 `template<typename NewScalar>`，正因搬到类外，才补上外层那行。）

### 2.2 `typename CastType<NewScalar, ModelTpl<...>>::type` —— traits + 依赖类型

返回类型不直接写 `ModelTpl<NewScalar,...>`，而绕道 traits 模板
（[../include/pinocchio/src/fwd.hxx](../include/pinocchio/src/fwd.hxx) 里 `template<typename NewScalar, class C> struct CastType;`）：

- **为什么用 traits**：`CastType<NewScalar, C>::type` = "把类型 `C` 换成 `NewScalar` 后的结果类型"，
  是一个**统一定制点**——`SE3`/`Inertia`/约束类等都各自特化 `CastType`，全库用同一写法表达"cast 后的类型"。
- **为什么加 `typename`**：`CastType<...>::type` 是**依赖名**（依赖模板参数 `NewScalar`），编译器无法
  自行判断 `::type` 是类型还是静态成员，**必须用 `typename` 声明"这是个类型"**。这是 C++ 硬性规则。

### 2.3 `.template cast<NewScalar>()` —— `.template` 消歧义符

```cpp
res.gravity = gravity.template cast<NewScalar>();
```

`gravity` 类型依赖模板参数，`cast` 又是它的模板成员。此时编译器会把 `cast<NewScalar>` 的 `<`
**误判成小于号**。加 `.template` 就是明确告知："`cast` 是模板，`<>` 是模板参数括号，不是比较。"

> 规律：`obj.template f<T>()` / `Type::template f<T>()` 只在 `obj`/`Type` 的类型**依赖外层模板参数**时才需要。
> 满库的 `.template cast<NewScalar>()` 都是这个原因。

### 2.4 "整数直接拷、数值才 cast" —— 跨类型逐字段重建

函数体一长串赋值，**分两类**，这是理解 cast 语义的关键：

```cpp
// (A) 拓扑/整数字段：与标量无关，直接原样拷贝
res.nq = nq;  res.parents = parents;  res.names = names;  res.idx_qs = idx_qs;  ...

// (B) 数值字段：内部含标量，必须换成 NewScalar
res.gravity            = gravity.template cast<NewScalar>();
for (k...) {
  res.inertias[k]        = inertias[k].template cast<NewScalar>();        // 空间惯量
  res.jointPlacements[k] = jointPlacements[k].template cast<NewScalar>(); // SE3
  res.joints[k]          = joints[k].template cast<NewScalar>();          // 关节 variant（递归 cast）
}
```

- **(A)**：`nq`/`parents`/`names`/`idx_qs`… 是维度、父子索引、字符串、下标，跟浮点标量无关，两个模板
  实例里类型相同，直接 `=`。
- **(B)**：`gravity`/`inertias`/`jointPlacements`/`joints`… 内部存 `Scalar`，逐个 `.cast<NewScalar>()` 转换。
- **为什么不能 `res = *this`**：`res` 是 `ModelTpl<NewScalar,...>`，与 `*this` 的 `ModelTpl<Scalar,...>`
  是**两个不同类型**，不能直接赋值——只能新建 `res` 后**逐字段搬**，数值字段搬时顺带换标量。
  这就是代码"啰嗦"的根因：它在**跨类型重建对象**。

### 2.5 小结

这段写法 = **类外成员模板（两行 template 头）** + **traits 定制点（`CastType<>::type`）** +
**依赖名消歧义（`typename` / `.template`）** + **跨类型逐字段重建（整数拷贝 / 数值 cast 二分）**。
语义就是指南 §11.2「玩具 2」的放大版：新建一个换了标量的模型，逐字段搬过去，数值字段搬时转类型。

## 3. autodiff：cast 到"会记账的标量"（为什么可以这样、如何实现）

**涉及文件**：[../include/pinocchio/autodiff/cppad.hpp](../include/pinocchio/autodiff/cppad.hpp)、
[../include/pinocchio/src/utils/static-if.hxx](../include/pinocchio/src/utils/static-if.hxx)、
[../include/pinocchio/src/autodiff/cppad/utils/static-if.hxx](../include/pinocchio/src/autodiff/cppad/utils/static-if.hxx)、
示例 [../examples/cppad/autodiff-rnea.cpp](../examples/cppad/autodiff-rnea.cpp)
**关联指南**：[§11.2 Tpl+context / autodiff](../PINOCCHIO_GUIDE.md)、本文档[条目 2（cast）](#2-modeltplcast-的模板写法四个-c-惯用法)

### 3.1 为什么可以这样（原理）

- **前提**：算法对标量"无知"。`rnea`/`aba` 是模板代码，只对标量做 `+ - * /`、`sin/cos`、比较等通用运算，
  不假设标量是 `double`。换一个"实现了这些运算的类型"，同一份算法就能跑。
- **关键**：`CppAD::AD<double>` 是"会记账的标量"。普通 `double` 只存值；`AD<double>` 存值的同时把每步
  运算记进一条**磁带（tape，即计算图）**。于是：**把算法用 AD 标量跑一遍 = 录下整张计算图；查这张图 =
  得到精确导数。** 这是指南 §11.2「玩具 3（Dual 双数）」的工业级版本（支持任意阶、反向模式、代码生成）。

### 3.2 实现三块拼图

**拼图 1：`model.cast<AD<double>>()`** —— 把整个模型换成 AD 标量（机制见[条目 2](#2-modeltplcast-的模板写法四个-c-惯用法)）。
此后模型里每个 SE3/惯量/极限向量的数值都是 AD 数，`rnea(ad_model, …)` 的一切运算都会被记账。

**拼图 2：适配层 [cppad.hpp](../include/pinocchio/autodiff/cppad.hpp)** —— 让 `AD<double>` "冒充"成合法标量。
它不实现任何机器人算法，只补齐 Eigen 和算法要求标量具备的东西：

```cpp
// ① Eigen 强制要求：能当矩阵标量的类型必须特化 NumTraits，否则 Eigen::Matrix<AD<double>> 编不过
template<class Base> struct Eigen::NumTraits<CppAD::AD<Base>> {
  typedef CppAD::AD<Base> Real; enum { IsInteger=0, IsSigned=1, RequireInitialization=1, ... };
  static AD<Base> epsilon(); static AD<Base> dummy_precision(); /* isApprox 用 */ ...
};
// ② 算法/Eigen 会调用的自由函数，给 AD 版重载
template<class Base> AD<Base> abs2(const AD<Base>& x){ return x*x; }
min/max/isfinite/conj/real/imag(...);  boost::math::constants::constant_pi<AD<Scalar>>;
// ③ 空间代数的 AD 特化实现
#include ".../cppad/spatial/se3-tpl.hxx"  ".../cppad/spatial/log.hxx" ...
```

> 一句话：**cppad.hpp 教会 Eigen 和 Pinocchio："`AD<double>` 也是正经标量，traits/数学函数/常量我都补上。"**
> 补齐后模板算法就无差别接受它。

**拼图 3：`static-if`** —— 让"带分支的代码"依然可微（**最关键、最易忽略**）。

普通分支在 AD 下会出错：录磁带时 `theta` 只有一个具体值，`if (theta<eps)` 只会把**当时走到的那条分支**
录进图 → 换输入再求导就用错分支 → **导数错误**。解法是把所有"依赖数值的分支"改写成
`if_then_else(op, lhs, rhs, then, else)`，按标量类型分派：

```cpp
// double：真正的 C++ if（src/utils/static-if.hxx），零开销
case LT: if (lhs < rhs) return then_value; else return else_value;
// AD<Scalar> 特化（src/autodiff/cppad/utils/static-if.hxx）：把两条分支+条件都录进磁带
case LT: return CppAD::CondExpLt<Scalar>(lhs, rhs, then_value, else_value);
```

`CondExpLt` 把**两条分支和条件一起**录进磁带，无论以后代入什么输入都能选对分支、给正确导数。这就是
`if_then_else` 在 `log/explog/四元数/SO3/SE3` 等含分支的数学里**被用了 70+ 处**的原因：让同一份代码在
`double` 下是普通 `if`、在 `AD` 下自动可微。

### 3.3 完整流程（[autodiff-rnea.cpp](../examples/cppad/autodiff-rnea.cpp)）

```cpp
ADModel ad_model = model.cast<AD<double>>();                   // 拼图1：换会记账的标量
Independent(ad_V);                                            // 声明"V 是自变量，开始录磁带"
ad_Y = pinocchio::rnea(ad_model, ad_data, ad_Q, ad_V, ad_A);  // 同一个 rnea 跑一遍 = 录图
ADFun<double> fun(ad_V, ad_Y);                               // 把磁带封成函数 V → tau
Eigen::VectorXd dtau_dv = fun.Jacobian(dv);                  // 查磁带 → ∂tau/∂V
```

示例随后与手写解析导数 `computeRNEADerivatives(...).dtau_dv` 对比，`isApprox` 通过。

### 3.4 澄清：自动微分 vs 解析梯度（勿混淆）

| | 自动微分（AD，本条目） | 解析梯度 |
|---|---|---|
| 来源 | `cast` 到 AD 标量、跑一遍、查磁带 | **手写**闭式导数（`rnea-derivatives.hxx`、`aba-derivatives.hxx`） |
| 通用性 | 对**任意**算法都能求导 | 每个算法**人工推导**一份 |
| 速度 | 慢（录带/求值开销） | 快（DDP 实时优化靠它） |
| 用途 | ①**验证**解析导数 ②无手写导数时兜底 ③CasADi 路径导出 C 代码 | 实时控制/轨迹优化主力 |

**结论**：Pinocchio 对外主打的"解析梯度"是**手写、更快**的；"cast 到会记账的标量"这条 AD 路线是
**通用机制 + 解析导数的校验器 + 代码生成入口**。二者互补，解析梯度并非由 AD 生成。

## 4. 通用关节 `joint-generic.hxx`：作用与模板特性

**涉及文件**：[../include/pinocchio/src/multibody/joint/joint-generic.hxx](../include/pinocchio/src/multibody/joint/joint-generic.hxx)
**关联指南**：[§11.2](../PINOCCHIO_GUIDE.md)、[§11.3 访问者](../PINOCCHIO_GUIDE.md)、[§11.4 JointCollection](../PINOCCHIO_GUIDE.md)、本文档[条目 2（cast）](#2-modeltplcast-的模板写法四个-c-惯用法)

### 4.1 在整个项目中的作用

本文件定义 3 个"通用关节"类型，是把 §11.4 的"关节类型目录（variant）"与 §11.3 的"访问者机制"**焊接在一起**的枢纽：

| 类型 | 是什么 | 谁在用 |
|------|--------|--------|
| `JointModelTpl` | **通用关节模型**（类型擦除后的统一句柄） | `model.joints[i]` |
| `JointDataTpl` | 通用关节数据 | `data.joints[i]` |
| `JointTpl` | 只借 `traits<>` 把 Model/Data 绑成一对的"标签类型" | CRTP 里的 `Derived` |

**核心结构：一个类同时"是 variant，又是 CRTP 基类的派生"**（[L256-258](../include/pinocchio/src/multibody/joint/joint-generic.hxx#L256)）：

```cpp
struct JointModelTpl
: JointModelBase<JointModelTpl<...>>          // 继承①：CRTP 基类 → 统一接口(id/nq/nv/calc…)
, JointCollectionTpl<...>::JointModelVariant  // 继承②：boost::variant<RX,RY,FreeFlyer,…>
```

多重继承使 `JointModelTpl` **同时具备两种身份**：作为 variant 能装任意具体关节、能被
`boost::apply_visitor` 直接分派；作为 `JointModelBase` 暴露统一接口、能整齐塞进 `std::vector<JointModel>`。
这正是 §11.3 里 `apply_visitor(visitor, jmodel)` 能对 `jmodel` 直接生效的原因——**`jmodel` 本身就 IS-A variant**。
`toVariant()` 即 `static_cast<JointModelVariant*>(this)`，下溯到 variant 子对象。

**它是"用 variant 实现的类型擦除外壳"**：几乎所有成员只是转发给自由函数（那些函数是访问者）：

```cpp
Transformation_t M() const { return joint_transform(*this); }   // 转发→访问者→具体关节的 M
int nq_impl()     const { return ::pinocchio::nq(*this); }
```

所以 `JointModelTpl` 是薄门面，自己不实现关节逻辑，每个操作都穿过 variant 派发到具体关节。
**Pinocchio 用 `boost::variant + visitor` 做类型擦除，而非虚函数**——有值语义、不进堆、静态分派。

> 一句话：没有本文件造出的 `JointModelTpl`/`JointDataTpl`，`model.joints[]` 这个混合类型容器和整个
> 访问者分派都不成立。

## 5. 朴素 variant 访问者三件套（`apply_visitor` 的最小写法）

**涉及文件**：[../include/pinocchio/src/multibody/joint/joint-basic-visitors.hxx](../include/pinocchio/src/multibody/joint/joint-basic-visitors.hxx)（`JointQVisitor` 等，约 1186-1210 行）
**关联指南**：[§11.3 CRTP + Boost.Fusion 访问者](../PINOCCHIO_GUIDE.md)、本文档[条目 4（类型擦除转发）](#4-通用关节-joint-generichxx的作用与模板特性)

`joint-basic-visitors.hxx` 里取"简单量"的访问者（`joint_q`/`joint_v`/`nq`/`shortname`…）用的是**最朴素、最标准的
`boost::variant` 访问者写法**，比 §11.3 的算法访问者简单得多，是理解 `apply_visitor` 的最佳样本。以 `JointQVisitor` 为例：

```cpp
template<typename Scalar, int Options, template<typename S,int O> class JointCollectionTpl>
struct JointQVisitor
: boost::static_visitor<typename JointDataTpl<...>::ConfigVector_t>   // ① "我是个返回 q 向量的访问者"
{
  typedef typename JointDataTpl<...>::ConfigVector_t ReturnType;

  template<typename JointDataDerived>                                 // ② 对每种具体关节数据各实例化一份
  ReturnType operator()(const JointDataBase<JointDataDerived> & jdata) const
  {
    return jdata.joint_q();                                           //    调具体关节自己的 joint_q()
  }

  static ReturnType run(const JointDataTpl<...> & jdata)
  {
    return boost::apply_visitor(JointQVisitor(), jdata);              // ③ 核心分派
  }
};

// 自由函数只是转发到 run
joint_q(const JointDataTpl<...> & jdata) { return JointQVisitor<...>::run(jdata); }
```

### 5.1 三件套逐块

- **① `struct XxxVisitor : boost::static_visitor<ReturnType>`** —— 定义一个"函子"（像函数一样可调用的对象）。
  继承 `boost::static_visitor<R>` 是 Boost.Variant 约定：声明"我是访问者，返回 `R`"。本身无数据成员，是空壳。
- **② 模板化 `operator()`** —— 函子被调用时执行的逻辑。因是模板，**对每种具体关节数据类型各生成一份**；
  此处 `jdata` 参数已是**具体类型**（如 `JointDataRX`），故 `jdata.joint_q()` 调的是 RX 那份实现。
  （"为何各生成一份"见 [5.1.1](#511-为什么模板-operator-会对每种关节各实例化一份)。）
- **③ `boost::apply_visitor(JointQVisitor(), jdata)`** —— 核心分派，三个易惑点：

| 写法 | 困惑 | 真相 |
|------|------|------|
| `JointQVisitor()` | 像"调用函数" | 不是调用，是**构造一个临时函子对象**（struct + `()` 默认构造，空壳） |
| `jdata` | 它是什么 | 通用 `JointDataTpl` **继承自 variant**（条目4），故 IS-A `boost::variant<JointDataRX,…>`，此刻装着某具体类型 |
| `apply_visitor(f,v)` | 怎么知道调哪个 `operator()` | **看 `v` 此刻装的具体类型**，调 `f.operator()(那个具体类型)`，等价编译期生成的 `switch` |

#### 5.1.1 为什么模板 `operator()` 会对每种关节各实例化一份

一句话：**`apply_visitor` 必须为 variant 里"每一种可能的类型"都备好一次调用，而这个 `operator()` 是模板，
"用一种类型调它"就会生成一份对应实例。**

- **前提**：`jdata` 的类型 `boost::variant<JointDataRX, JointDataRY, …, JointDataFreeFlyer>` 的可能类型清单
  **编译期已固定**（来自 §11.4 的 JointCollection）。运行时只装其中一种，但编译期不知是哪种。
- **推论**：既然编译期不知运行时装哪种，`apply_visitor` 就必须**覆盖所有可能**，生成的代码概念上等价于：

```cpp
switch (jdata.which()) {                                          // 运行时"装的是第几种"
  case 0: return visitor(boost::get<JointDataRX>(jdata));         // 用 JointDataRX 调 → 实例化 operator()<JointDataRX>
  case 1: return visitor(boost::get<JointDataRY>(jdata));         // 用 JointDataRY 调 → 实例化 operator()<JointDataRY>
  case 2: return visitor(boost::get<JointDataFreeFlyer>(jdata));  // …每种类型一个 case
  ...
}
```

- **本质**：函数模板是"配方"，不是代码——只有用某具体类型调用它，编译器才**实例化**出一份真函数。
  上面每个 `case` 用不同具体类型调 `operator()`，于是 `jdata.joint_q()` 在各份里分别解析成 RX 版 / RY 版 /
  FreeFlyer 版…… **variant 有 N 种关节 → N 次不同类型调用 → N 份实例**。

**所以"各实例化一份"不是刻意设计，而是"模板 + 被 N 种类型分别调用"的必然结果。** 它等价于你手写了 N 个
重载 `operator()(const JointDataRX&)` / `(const JointDataRY&)` / …，但函数体只写一遍，编译器替你盖章复印。
每份实例都具体、可内联，分派又是跳表——这就是 §11.3 说的"零成本抽象"：写起来像一个函数应对所有关节，
编译后却是 N 份专门代码 + 一张跳表，无虚函数。

> 记忆：**是"编译期已知的有限类型集合（variant 的类型清单）"驱动了 N 份实例化。**

### 5.2 为什么要绕这一圈

外层 `jdata` 是通用 variant，**没有可直接调的 `joint_q()`**——必须先知道它装的是哪种关节。`apply_visitor`
干的就是"从 variant 拆出具体类型、再调具体实现"。这是条目 4「类型擦除靠转发」的最小实例，完整链：

```
JointDataTpl::joint_q()             // joint-generic.hxx 的成员（算法里调的）
  └─ ::pinocchio::joint_q(*this)    // 转发给自由函数
       └─ JointQVisitor::run(jdata) // 自由函数转发给访问者
            └─ apply_visitor(JointQVisitor(), jdata)          // 按具体类型分派
                 └─ operator()(JointDataRX&){ return jdata.joint_q(); }  // 落到具体关节
```

### 5.3 与 §11.3 算法访问者的区别

| | 本例 `JointQVisitor`（朴素版） | §11.3 `JointUnaryVisitorBase`（算法版） |
|---|---|---|
| 分派谁 | 只分派一个 variant（`jdata`） | 分派 `jmodel`，还要配对取出 `jdata` |
| 额外参数 | 无 → **不需要 Boost.Fusion** | 有（model/data/q…）→ Fusion 打包转发 |
| 写法 | 直接继承 `boost::static_visitor`，写 `operator()` | 继承 CRTP 基类 `JointUnaryVisitorBase<自己>`，写 `algo()` |
| 用途 | 取一个简单量（q/v/nq/名字…） | 跑一趟完整算法（FK/RNEA 的一个 Step） |

**记忆**：`boost::static_visitor` + 模板 `operator()` + `apply_visitor(函子(), variant)` 是**最原始的 variant
分派三件套**；§11.3 那套是在其上加了 CRTP 和 Fusion 的增强版。

## 6. `joint-basic-visitors.hxx`：通用关节的"基础操作 API 集"

**涉及文件**：[../include/pinocchio/src/multibody/joint/joint-basic-visitors.hxx](../include/pinocchio/src/multibody/joint/joint-basic-visitors.hxx)（约 1653 行）
**关联指南/条目**：[§11.3 访问者](../PINOCCHIO_GUIDE.md)、[条目 4（类型擦除外壳）](#4-通用关节-joint-generichxx的作用与模板特性)、[条目 5（三件套）](#5-朴素-variant-访问者三件套apply_visitor-的最小写法)

### 6.1 整体定位

本文件（`namespace pinocchio`）提供一整套**作用在"通用关节"上的自由函数 API**。它们不实现任何关节逻辑，
而是用[条目 5](#5-朴素-variant-访问者三件套apply_visitor-的最小写法)的"访问者三件套"，把对 `JointModelTpl`/`JointDataTpl`
（类型擦除外壳，见[条目 4](#4-通用关节-joint-generichxx的作用与模板特性)）的调用**转发到里面装的具体关节**。

它正是[条目 4](#4-通用关节-joint-generichxx的作用与模板特性)里那些成员方法（`M(){return joint_transform(*this);}`、
`nq_impl(){return nq(*this);}`…）**真正委托的落点**。

> 一句话：区别于 `kinematics.hxx`/`rnea.hxx` 那种"跨关节遍历的算法"，这里每个函数只对**单个关节**做一件
> 基础事（取 q、取 M、查 nq、算 calc…），且全靠 `apply_visitor` 转发到具体关节类型。它是连接"通用关节
> 外壳"与"具体关节实现"的**桥接 API 层**。

### 6.2 按用途分组

**① 构造**

每个自由函数的实现都是同一套路——[条目 5](#5-朴素-variant-访问者三件套apply_visitor-的最小写法) 的三件套。以 `nq` 为例：

```cpp
struct JointNqVisitor : boost::static_visitor<int> { /* operator() 对每种关节返回其 nq */ };
inline int nq(const JointModelTpl<...> & jmodel) {
  return JointNqVisitor<...>::run(jmodel);   // 内部 boost::apply_visitor(...)
}
```

## 7. `JointModelTpl` 的 calc/calc_aba/配置切片转发层（模板惯用法集萃）

**涉及文件**：[../include/pinocchio/src/multibody/joint/joint-generic.hxx](../include/pinocchio/src/multibody/joint/joint-generic.hxx)（`JointModelTpl` 成员，约 354-413 行）
**关联指南/条目**：[§11.3 访问者](../PINOCCHIO_GUIDE.md)、[条目 4（类型擦除外壳）](#4-通用关节-joint-generichxx的作用与模板特性)、[条目 6（基础操作 API）](#6-joint-basic-visitorshxx通用关节的基础操作-api-集)、[条目 2.2（依赖名）](#2-modeltplcast-的模板写法四个-c-惯用法)

这组成员都是通用 `JointModelTpl` 的**转发方法**（类型擦除门面），但密集示范了多种模板技巧。

### 7.1 三个 `calc()` 重载 —— 单关节运动学转发入口

```cpp
template<typename ConfigVector>                                 // (a) 只有 q
void calc(JointDataDerived & data, const Eigen::MatrixBase<ConfigVector> & q) const
{ calc_zero_order(*this, data, q.derived()); }

template<typename TangentVector>                                // (b) 只有 v（用 Blank 占位）
void calc(JointDataDerived & data, const Blank blank, const Eigen::MatrixBase<TangentVector> & v) const
{ calc_first_order(*this, data, blank, v.derived()); }

template<typename ConfigVector, typename TangentVector>         // (c) q 和 v 都有
void calc(JointDataDerived & data, const Eigen::MatrixBase<ConfigVector> & q,
          const Eigen::MatrixBase<TangentVector> & v) const
{ calc_first_order(*this, data, q.derived(), v.derived()); }
```

- **转发**给自由函数 `calc_zero_order`/`calc_first_order`（条目 6 ②，内部 `apply_visitor` 派发到具体关节）。
- **`q.derived()`**：Eigen CRTP 惯用法。参数收成 `Eigen::MatrixBase<T>&`（Eigen 所有矩阵/表达式的 CRTP 基类），
  `.derived()` 还原成具体表达式 → 一个模板即可接受 `VectorXd`/块表达式/`Ref`/numpy 切片，零拷贝。
- **`Blank` 标签消歧**（难点）：(a) 与 (b) 都"只带一个向量参数"，签名会撞车。(b) 硬塞空类型 `Blank` 占位变成
  `(data, Blank, v)`，与 (a) 的 `(data, q)` 区分——**tag dispatch**。调用方 `calc(data, Blank(), v)` 明确"传的是速度"。
- **与 §11.3 的区别**：这里是**通用关节**的 `calc`（转发时再拆箱）；§11.3 FK 的 `algo` 里 `jmodel` 已被
  `apply_visitor` 拆成**具体** `JointModelRX`，那里的 `jmodel.calc` 直接绑到 RX 自己的 `calc`、不再二次派发。
  同名 `calc`，一个"泛型转发版"、一个"具体直调版"。

### 7.2 `lieGroup_impl` —— 只声明、延迟定义

```cpp
template<typename LieGroupMap>
typename LieGroupMap::template operation<JointModelTpl>::type lieGroup_impl() const;  // 无函数体
// 注释：must be defined after Lie group and joint visitors
```

- **只声明不定义**：必须等 Lie group 与关节访问者都定义完再实现，否则类型不完整——**声明/定义分离**破解头文件循环依赖。
- 返回类型是**元函数**：给定关节类型算出其**李群操作类型**（旋转关节→ℝ¹ 向量空间，浮动基→SE(3) 群…），
  决定该关节 `integrate`/`difference` 走哪套流形运算（§2.1）。`::template ... ::type` 是依赖名消歧（条目 2.2）。

### 7.3 `calc_aba` —— ABA 单关节步转发

```cpp
void calc_aba(JointDataDerived & data, const Eigen::MatrixBase<VectorLike> & armature,
              const Eigen::MatrixBase<Matrix6Like> & I, const bool update_I) const
{ ::pinocchio::calc_aba(*this, data, armature.derived(), I.const_cast_derived(), update_I); }
```

- 转发给自由函数 `::pinocchio::calc_aba`（ABA 单关节计算，§4.4）。
- **`I.const_cast_derived()`**：Eigen 惯用法，把 `const MatrixBase<...>&` **去 const** 再取具体类型。因为 ABA 要
  **原地修改** `I`（关节化体惯量），但 Pinocchio 约定输入输出矩阵形参统一写 `const MatrixBase&`，真正写入时用
  `const_cast_derived()` 打开写权限。**见到它就知道：这是"名义 const、实则输出"的参数。**

### 7.4 两个 `JointMappedConfigSelector_impl` —— 取"本关节那段"配置

const / 非 const 成对，逻辑相同，只是返回可读/可写：

```cpp
template<typename D>
typename SizeDepType<NV>::template SegmentReturn<D>::ConstType     // 返回类型是"算出来的"
JointMappedConfigSelector_impl(const Eigen::MatrixBase<D> & a) const
{
  typedef ... ReturnType;
  typedef JointMappedConfigSelectorVisitor<InputType, ReturnType> Visitor;   // 定制访问者
  typename Visitor::ArgsType arg(a);                                          // 打包参数
  return Visitor::run(*this, arg);                                            // 跑访问者（apply_visitor）
}
```

- **作用**：从"完整配置空间大小"的大向量 `a` 里，按本关节的 `idx_q`/`nq` 切出属于它的那一段。
- **`SizeDepType<NV>::template SegmentReturn<D>::ConstType`**：**按编译期尺寸决定返回类型**的元函数，据 `NV`
  选正确的 Eigen 段/块表达式类型。此处 `NV=Dynamic`（通用关节尺寸运行时才知，条目 4 要点），故返回动态段类型。
- **const/非 const 成对**：const 版返 `::ConstType`（只读段），非 const 版返 `::Type`（可写段）——标准访问器对偶。
- **内部就是 §11.3 带参访问者**：定义 `Visitor` → 构造 `ArgsType arg(a)` 打包 → `Visitor::run(*this, arg)` 分派。
  是访问者机制的一次**就地手工使用**。

| 惯用法 | 出现处 | 一句话 |

## 8. `forwardKinematics` 驱动器：扁平遍历 + 每关节分派

**涉及文件**：[../include/pinocchio/src/algorithm/kinematics.hxx](../include/pinocchio/src/algorithm/kinematics.hxx)（`forwardKinematics` config-only 重载 + `ForwardKinematicZeroStep`）
**关联指南/条目**：[§4.1 FK](../PINOCCHIO_GUIDE.md)、[§11.3 访问者](../PINOCCHIO_GUIDE.md)、[条目 4-7](#4-通用关节-joint-generichxx的作用与模板特性)

前面条目 4-7 讲"单个关节"的机制，本条目上升到"**整趟算法怎么跑**"。`forwardKinematics` 是驱动整个访问者机构的
**外层循环**——§11.3 的"一次 `run` 分派"在这里被套进 `for`，对每个关节各跑一次。

### 8.1 整体执行策略：拓扑有序的扁平遍历（非递归）

虽然运动学是棵树，但这里**没有递归**，就是从 1 到 `njoints` 的普通 `for`。能成立靠一个关键不变量：

> **`model.joints[]` / `model.parents[]` 是拓扑排序的——父关节下标永远小于子关节。**

于是正向扫 `i=1..n` 时，处理到 `i` 之前它的父 `parent(i)` 一定已算完，故递推
`oMi[i] = oMi[parent] * liMi[i]` 永远合法。**这就是 FK 为何 $O(n)$、无递归、缓存友好**：把树递推压平成对有序数组的线性扫描。

- **从 `i=1` 起**（非 0）：下标 0 是"universe/世界根"虚拟固定关节，`oMi[0]` 恒为单位阵，无需算。
- **两级分派**：外层 `for`（遍历顺序）× 内层 `Algo::run`→`apply_visitor`→`algo<具体关节>`（每种关节各干什么），两者正交。

```
forwardKinematics
  └─ for i = 1..njoints            ← 外层：扁平遍历（本条目关注点）
       └─ Algo::run(joints[i], …)  ← 内层：一次访问者分派（§11.3）
            └─ apply_visitor → algo<具体关节>(…)
```

### 8.2 逐行解析

```cpp
void forwardKinematics(const ModelTpl<...> & model, DataTpl<...> & data,
                       const Eigen::MatrixBase<ConfigVectorType> & q)
{
  PINOCCHIO_CHECK_ARGUMENT_SIZE(q.size(), model.nq, "...");   // ① 运行时入参维度校验（q.size==nq）
  assert(model.check(data) && "...");                        // ② 仅 Debug 期 model/data 一致性
  typedef typename ModelTpl<...>::JointIndex JointIndex;      // ③ 依赖类型别名
  typedef ForwardKinematicZeroStep<...> Algo;                // ④ 把这趟访问者绑成短名
  for (JointIndex i = 1; i < (JointIndex)model.njoints; ++i) // ⑤ 拓扑有序扁平遍历
    Algo::run(model.joints[i], data.joints[i],
              typename Algo::ArgsType(model, data, q.derived()));  // ⑥ 每关节一次分派
}
```

第 ⑥ 行三实参：`model.joints[i]`（通用关节模型，IS-A variant，条目4）、`data.joints[i]`（配对数据）、
`Algo::ArgsType(model, data, q.derived())`（Boost.Fusion 元组打包额外参数，§11.3 技巧C；`q.derived()` 还原 Eigen 具体类型）。

### 8.3 每次迭代内部：`algo` 做的事

`Algo::run` 经 `apply_visitor` 落到 `ForwardKinematicZeroStep::algo<具体关节>`：

```cpp
const JointIndex i = jmodel.id();  const JointIndex parent = model.parents[i];
jmodel.calc(jdata.derived(), q.derived());              // (1) 由 q 算本关节局部变换，写进 jdata
data.liMi[i] = model.jointPlacements[i] * jdata.M();    // (2) 关节相对父的变换
data.oMi[i]  = (parent > 0) ? data.oMi[parent] * data.liMi[i] : data.liMi[i];  // (3) 递推到世界系
```

数据流：**q → `jmodel.calc` → `jdata.M()`（转角变换）→ `liMi`（乘固定安置=相对父）→ `oMi`（乘父世界位姿=世界系）**。
对照 §4.1 的 ${}^0T_i = {}^0T_{p(i)} \cdot {}^{p(i)}T_i(q_i)$：`jdata.M()`=随 $q_i$ 变的部分，`jointPlacements[i]`=固定安置，
二者积 `liMi`=${}^{p(i)}T_i(q_i)$，再乘 `oMi[parent]`=${}^0T_{p(i)}$ 得 `oMi[i]`。

### 8.4 涉及的方法清单

| 方法 / 调用 | 出处 | 作用 |
|-------------|------|------|
| `PINOCCHIO_CHECK_ARGUMENT_SIZE` | 宏 | 运行时入参维度校验 |
| `model.check(data)` | Model | Debug 期一致性 |
| `q.derived()` | Eigen CRTP | 还原具体表达式 |
| `Algo::run(jmodel, jdata, args)` | `JointUnaryVisitorBase`（条目5/§11.3） | 触发一次关节类型分派 |
| `Algo::ArgsType(...)` | Boost.Fusion | 打包额外参数包 |
| `jmodel.id()` / `model.parents[i]` | JointModel / Model | 本关节 / 父关节下标 |
| `jmodel.calc(jdata, q)` | JointModel（条目7） | 由 q 算局部变换 |
| `jdata.M()` | JointData（条目6④） | 关节相对变换 SE3 |
| `model.jointPlacements[i]` | Model | 关节固定安置 |
| `SE3::operator*` | spatial/se3 | 变换复合 |
| `data.liMi[i]` / `oMi[i]` / `oMi[parent]` | Data | 关节相对 / 世界位姿存取 |

### 8.5 通用骨架

**外层扁平遍历 + 内层类型分派**是 Pinocchio 所有 $O(n)$ 算法（RNEA/ABA/CRBA…）共用的执行骨架：
换掉 `algo()` 体，`for` 驱动不变。RNEA 是"正扫一趟 + 反扫一趟"，ABA 是三趟，本质都是若干次这样的遍历。

## 9. 分派内环：参数打包、拆包与 `::template` 语法

**涉及文件**：[../include/pinocchio/src/multibody/visitor/joint-unary-visitor.hxx](../include/pinocchio/src/multibody/visitor/joint-unary-visitor.hxx)（`run` / `InternalVisitorModelAndData::operator()`）、[../include/pinocchio/src/multibody/visitor/fusion.hxx](../include/pinocchio/src/multibody/visitor/fusion.hxx)（`append`）
**关联指南/条目**：[§11.3 访问者](../PINOCCHIO_GUIDE.md)、[条目 5（三件套）](#5-朴素-variant-访问者三件套apply_visitor-的最小写法)、[条目 8（FK 驱动器）](#8-forwardkinematics-驱动器扁平遍历--每关节分派)

本条目聚焦"参数如何从 `run` 一路传到你的 `algo`"——即 `Algo::run(joints[i], data.joints[i], ArgsType(...))`
里那个 `ArgsType` 的**打包 → 穿过分派 → 拆包**全过程，以及其中最难读的 `&...::template algo<...>` 语法。

### 9.1 为什么把额外参数打包成 `ArgsType`

`run` 内部必须走 `boost::apply_visitor(visitor, jmodel)`，而 `apply_visitor` 的接口**只收两样**：一个函子 + 一个
variant。它没有位置传 `model/data/q/v`。三个原因决定必须打包：

1. **接口是死的**：额外参数只能**先藏进函子对象**（作为数据成员）随行，分派后再取出——所以必须是一个能存储、
   可延迟使用的**值**。
2. **各算法参数列表不同**：FK-zero 是 `(model,data,q)`、FK-first 是 `(model,data,q,v)`、RNEA 更多。若 `run` 签名
   写死就得每种写一个。于是 `run` 只认一个笼统的 `ArgsTmp args`，`ArgsType`（Boost.Fusion 元组）把 N 个异构参数
   压成 1 个值。
3. **Fusion 一进一出**：`ArgsType(...)` 打包、`bf::invoke` 拆包（见 9.2），中间旅程用统一签名承载任意参数。

> 为什么不用 C++ 可变参数包 `Args&&...`？因为参数包不是"可存进对象的值"，而这里恰需把它存成函子成员等回调时用。
> `fusion::vector`+`invoke` 本质是 Boost 版的 `std::tuple`+`std::apply`。

### 9.2 `operator()`：拆箱 + 拼参 + 调用

`apply_visitor` 分派后落到 `InternalVisitorModelAndData::operator()`（[L229-239](../include/pinocchio/src/multibody/visitor/joint-unary-visitor.hxx#L229)）：

```cpp
template<typename JointModelDerived>                                    // 每种关节各实例化一份（条目5.1.1）
ReturnType operator()(const JointModelBase<JointModelDerived> & jmodel) const
{
  typedef typename helper::add_const_if_const<                         // ② 推配对 JointData 类型 + 传 const
    JointData, typename JointModelBase<JointModelDerived>::JointDataDerived>::type  JointDataDerived;
  return bf::invoke(                                                   // ⑤ 拆包+调用
    &JointVisitorDerived::template algo<JointModelDerived>,            // ④ 目标函数指针（见 9.3）
    bf::append(                                                       // ③ 拼参数序列
      boost::ref(jmodel.derived()),
      boost::ref(boost::get<JointDataDerived>(jdata)),
      args));
}
```

- **② 推配对类型**：`JointModelBase<X>::JointDataDerived` 给出 X 配对的 Data 类型（RX→JointDataRX）；
  `add_const_if_const` 若函子存的 `jdata` 是 const 就给取出类型也加 const（只读算法的常量正确性）。
- **③ 拼参数**：
  - `boost::get<JointDataDerived>(jdata)`：从 jdata variant **拆箱**出具体 `JointDataRX&`（配对不变量保证不抛，条目4）。
  - `boost::ref(...)`：让 jmodel/jdata **以引用**进元组。**对 jdata 是正确性问题**——`algo` 里 `jmodel.calc(jdata,…)`
    要写入 jdata，若被拷贝则写入落到副本、结果丢失；`boost::ref` 保证是同一对象。
  - `bf::append`（[fusion.hxx:49-60](../include/pinocchio/src/multibody/visitor/fusion.hxx#L49)）是自定义辅助，
    语义"把前导元素 `push_front` 到尾部序列前面"：`append(jmodel, jdata, args) = [jmodel, jdata, <args 展开>]`
    = `[jmodel, jdata, model, data, q, v]`。（名字叫 append 略误导，实为"前端插入"。）
- **⑤ `bf::invoke(f, seq)`**：把序列摊平成实参喂给 f，等价 `algo<JointModelRX>(jmodel, jdata, model, data, q, v)`，
  正好对上 `ForwardKinematicZeroStep::algo` 签名（条目8.3）。

**一句话**：`get` 拆箱取配对 jdata → `append` 把 jmodel/jdata 补到共享 args 前面凑完整实参 → `invoke` 摊开调到
CRTP 定位的 `algo`。三技巧在此 8 行全落地：`get`=Variant、`JointVisitorDerived::algo`=CRTP、`append`+`invoke`=Fusion。

### 9.3 `&JointVisitorDerived::template algo<JointModelDerived>` 语法详解

三个语法点叠加，逐层搭：

1. **`&类::函数` = 取函数地址**。因 `algo` 是 `static`（无 `this`），得到**普通函数指针**，正是 `invoke` 要的可调用 `f`。
2. **`algo<JointModelDerived>` = 指定模板实例**。`algo` 是模板函数（配方），取地址须说清要哪一份实例。
   若类名是具体类型，`&Foo::algo<JointModelRX>` 就够了。
3. **`::template` = 消歧关键字**。这里类名是**模板参数** `JointVisitorDerived`（依赖类型），编译器解析时
   还不知 `algo` 是模板，会把 `<` 当**小于号**。`template` 关键字手动声明"`algo` 是模板、`<>` 是模板参数括号"。

> 规律：`::` 左边是依赖类型、右边是模板成员 → 必须加 `template`。与[条目 2.3](#2-modeltplcast-的模板写法四个-c-惯用法)
> 的 `.template cast<>()` 同一规则，区别只是 `::`（访问类型成员）vs `.`（访问对象成员）：
>
> | 写法 | 场景 |
> |------|------|
> | `对象.template 成员<...>` | 通过对象访问依赖类型的模板成员 |
> | `类型::template 成员<...>` | 通过类型访问依赖类型的模板成员（本行） |

代入具体类型即一目了然：当 `JointVisitorDerived=ForwardKinematicZeroStep`、`JointModelDerived=JointModelRX`：

```cpp
&JointVisitorDerived::template algo<JointModelDerived>
  ≡  &ForwardKinematicZeroStep::algo<JointModelRX>   // 指向这个具体静态函数的指针
```

**整体含义**：取"访问者类里那个静态模板函数 `algo`、用具体关节类型实例化出的那一份"的函数指针，交给 `invoke` 调用。
